# Agent Fleet project instructions

These instructions apply to this repository. Respond to the human in Spanish;
preserve code, commands and identifiers. Respect the current task's authority
and existing work. Do not import another repository's procedures.

## Scope and roles

For substantive work state the objective, current evidence, constraints and
observable success criteria. Inspect for reviews; implement when authorized.
Continue authorized local changes through relevant verification. Report facts,
inferences and missing evidence separately. Do not create agents, tasks or live
provider campaigns unless explicitly authorized. Only the registered Worker
edits a Mission's candidate; Lead, Reviewer and Verifier are readers. A local
maintenance task may have one explicitly assigned implementer instead.

Herdr stages are Plan, Build, Review, Verify and Synthesis. Each stage judges its
own supplied success criteria. A failing baseline may inform a valid Plan.
Do not wait for future stages to return a stage PASS. Stage PASS, transport
completion, artifact acceptance and Mission success are distinct claims.

## Acceptance and permissions

The controller ledger, immutable CAS evidence, frozen candidate, independent
archive verification and configured acceptance contracts determine closure.
Screenshots, exit zero, model self-reports and green tests alone do not prove
semantic success. Report exactly which behavior and boundary were checked.

Artifact predicates validate pinned files. The optional functional contract
adds a separate result over the frozen tree. The current Python stats profile
accepts a limited source subset and a fixed RPC/test protocol; it is not a
general hostile-Python runner. OS isolation, runtime permission attestation,
source acceptance and functional behavior are separate layers.

Never treat a prompt, writable path or tool availability as permission. Mission
roles must obey the supplied authority and output contract. They must not commit,
push, deploy, spend, send messages, change global settings or touch unrelated
resources unless the current task explicitly authorizes that action and scope.
An isolated maintenance fixture may create its own Git history when authorized;
that does not authorize commits in the working repository. Preserve user changes.

## Lifecycle and recovery

Use explicit Mission, runs directory and Herdr session identities. Supervision
is a bounded foreground observer of one Mission, not a second fleet. Persist
pause/cancel requests independently of the driver lock. Requested pause is not
confirmed pause. Resume reuses durable evidence and keeps original deadlines.
Cancel only exact owned run/generation resources; a result can arrive before
cancellation. Confirm quiescence and functional container cleanup before closure.
After ambiguous send, reconcile the same run; do not blindly resend or promise
exactly-once delivery. Terminal historical records remain read-only.

Keep the historical CMUX readers and explicitly selected legacy workflows
compatible. Do not introduce CMUX fallback into the Herdr lane. Do not run live
Herdr/Codex campaigns, install software, pull images or broaden cleanup as an
implicit test step. Use existing local dependencies and provider-free fixtures.

## Instructions and evidence

The Herdr controller snapshots applicable tracked target instructions from the
candidate baseline and supplies their content, scope and hashes to all roles.
The supplied operational task bounds their authority. Do not assume global
skills, the coordinator's conversation or another role's instructions are
inherited. Preserve the required result protocol; put citations inside its
summary when raw JSON is required. Model/effort identity comes from the bound
transcript, not configuration or a role's guess; unavailable identity is not by
itself a stage blocker.

See `docs/herdr-mission-control.md`, `docs/herdr-functional-checks.md`,
`docs/herdr-supervision-and-measurement.md` and `docs/herdr-instruction-scope.md`.
For maintenance verification use relevant `python3 -B -m unittest` modules and
`git diff --check`. Docker tests require the explicit existing local test lane;
real model quality and billed cost remain NOT_VERIFIED without that evidence.
