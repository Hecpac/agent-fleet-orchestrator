01 · porque

Escala tu cómputo para escalar tu impacto

La tesis del video es una sola frase, y es la vara con la que se mide cualquier herramienta de orquestación:

“Un agente que no puedes ver es un agente que no puedes mejorar.” IndyDevDan — la diferencia entre vibe coding y agentic engineering

Orquestar no es esconder agentes detrás de un SDK: es tener cada agente en una superficie visible, direccionable y programable. Dan plantea tres problemas que cualquier ingeniero con más de dos agentes reconoce — y evalúa si cmux los resuelve:

problema #1

Acceso agéntico

Sin acceso programático a tus agentes, tú eres el cuello de botella: cada arranque, cada prompt y cada lectura pasa por tus manos.

✓ resuelto · CLI + socket Unix a cada terminal: un agente opera a otros agentes igual que un humano.

problema #2

Agentes medibles

Necesitas ver cada agente (Claude, Codex, MiniMax…) para saber qué salió bien y reforzar ese comportamiento — o interrumpir a tiempo.

✓ resuelto · panes por rol, tabs con identidad, colores por workspace, notificaciones y salto rápido a cualquier agente.

problema #3

Arranques instantáneos

Bootear un equipo a mano mata la velocidad agéntica: 8 panes, 8 comandos, 8 contextos… cada vez.

✓ resuelto · session files y layouts declarativos reutilizables; en tu repo: un comando (just fleet).

Contrapeso del propio Dan: los labs tienen incentivos para que quemes tokens (tokenmaxxing). Más agentes no es más impacto: agentes visibles y verificados es más impacto. Los problemas van primero; las herramientas, después.
02 · que-es

Qué es cmux (y qué no es)

cmux es un terminal nativo de macOS (Swift + AppKit) construido sobre libghostty — el motor de renderizado de Ghostty como librería, igual que una app usa WebKit. Es open source (GPL-3.0-or-later, de Manaflow) y se define como “a primitive, not a solution”: piezas componibles, no un workflow impuesto. Cualquier agente que corra en un terminal funciona sin integración: Claude Code, Codex, OpenCode, Gemini CLI, Aider, Goose…

organización

Sidebar con tabs verticales

Cada workspace muestra rama git, PR vinculado, directorio, puertos escuchando y su última notificación. Un vistazo = estado de la flota.

atención

Anillos de notificación

Los panes piden atención con un anillo azul; los tabs se encienden con badges. Escape sequences estándar (OSC 9/99/777) y ⌘⇧U salta al último no leído.

programabilidad

CLI + socket API

Crear workspaces, dividir panes, enviar teclas, leer pantallas, notificar y automatizar el browser — todo por línea de comandos.

web

Browser embebido scriptable

Un pane de navegador junto al terminal: navegar, click, llenar formularios, snapshot del DOM, evaluar JS. Importa sesiones de Chrome, Firefox, Arc…

remoto

SSH de primera clase

cmux ssh user@host crea workspaces remotos; el browser enruta por la red remota (localhost “simplemente funciona”). Puede adjuntarse a tmux remoto.

durabilidad

Sesiones que sobreviven

Ventanas, workspaces, panes, cwd y scrollback se restauran tras relanzar — incluso tras reiniciar la máquina. Hooks de agente permiten claude --resume.

instalación
# Homebrew
brew tap manaflow-ai/cmux
brew install --cask cmux

# La app renderiza con tu config de Ghostty (~/.config/ghostty/config):
# temas, fuentes y colores se heredan. Config propia: ~/.config/cmux/cmux.json
03 · modelo-mental

Cinco contenedores anidados

Todo en cmux vive en una sola jerarquía. Si tienes claro este dibujo, cada comando del CLI se vuelve obvio: siempre estás nombrando uno de estos niveles.

Windowuna ventana de macOS con su sidebar
Workspaceuna entrada del sidebar — un equipo, una misión
Paneuna región dividida dentro del workspace
Surfaceun tab dentro del pane: terminal o browser — lo que direccionas
Panelel contenido renderizado

Los comandos imprimen las referencias que crean — OK surface:7 pane:7 workspace:5 — y con esas refs cortas (workspace:5, surface:7) diriges todo lo demás.

Las refs cortas son posicionales, no identidades. Una ref obsoleta puede resolver a otro surface. Incidente real en tu repo: un close-surface con ref vieja cerró el pane del lead vivo (se recuperó con claude --resume). Regla dura: tree o manifest primero, siempre; UUIDs para acciones destructivas.
04 · loop-de-control

Cuatro verbos: send → read → decide → repeat

Toda la orquestación colapsa en un loop mínimo. Un orquestador que domina estos cuatro verbos puede levantar, dirigir y desmontar una flota entera — es exactamente lo que prueban los 31 prompts de learning-cmux-with-agents.

verbo 1 · escribircmux send

Teclea texto en un terminal, como si fueras tú. No pulsa enter.

verbo 2 · pulsarcmux send-key

Pulsa una tecla con nombre: enter, escape, tab, ctrl-c.

verbo 3 · leercmux read-screen

Lee lo que el terminal imprimió (con --scrollback para historia).

verbo 4 · cerrarcmux close-surface

Apaga la superficie cuando la misión termina.

ciclo completo sobre un agente
cmux ping                                             # ¿la app vive? → PONG
cmux tree --all                                       # mapa de todo lo que existe
cmux new-workspace --name "audit" --cwd ~/repo --focus false
cmux new-pane --direction right --workspace 5 --focus false
cmux send --surface 7 --workspace 5 'explica el bug de scripts/foo.sh'
cmux send-key --surface 7 --workspace 5 enter          # send NO pulsa enter
cmux read-screen --surface 7 --workspace 5 --lines 40  # nunca asumas: lee
cmux close-surface --surface 7                         # tree PRIMERO si la ref no es fresca

Identidad visual desde el CLI

La visibilidad a escala se construye con los helpers: nombra, colorea y reporta estado para que una flota de 8 se lea de un vistazo.

helpers de visibilidad
cmux rename-tab --surface 7 "BUILD·codex"
cmux workspace-action --action set-color --workspace 5 --color "#7C3AED"
cmux set-status build "running" ; cmux set-progress 0.7 --label "tests"
cmux notify --title "fleet-audit" --body "2 P0 confirmados"
cmux trigger-flash
  • send no pulsa enter. Siempre va seguido de send-key … enter. Los TUIs interactivos se interrumpen con escape; los shells one-shot con ctrl-c.
  • read-screen después de actuar. Nunca asumas que un comando funcionó — el loop es send → read → decide.
  • Quotea con cuidado. El texto de send pasa primero por tu shell: payload en comillas simples, escapa las internas.
  • Nunca promptees un surface que no identificaste en tree o en un manifest. Lo mismo antes de cerrar.
05 · eventos-no-polling

El patrón timbre: espera eventos, no relojes

Releer pantallas en un loop quema tokens y añade latencia. cmux emite un event stream: te suscribes, duermes, y el evento (el “timbre”) te despierta con los IDs de workspace/surface — entonces vas a buscar el detalle una sola vez.

event stream
# stream crudo (hooks de agentes + notificaciones), con reconexión durable
cmux events --name agent.hook --name notification.created --reconnect --cursor-file .cmux-cursor

# en tu repo el patrón ya está empaquetado — despacha y bloquea en el evento exacto:
./scripts/fleet-send.sh audit codex "revisa el diff del PR #42"
./scripts/fleet-wait.sh audit codex --run codex=<run_id> --timeout 1800
cmux read-screen --surface <s> --workspace <ws> --lines 50   # una sola lectura, al final

La regla de tu repo lo resume mejor que cualquier doc oficial: panes para VER, archivos para DATOS, eventos para SEÑALES. Las pantallas truncan (panes angostos, TUIs que redibujan), los títulos de notificación viajan redactados, y el polling cuesta. Findings grandes → archivo; completado → evento; supervisión → pane.

fleet-wait devuelve estado tipado — exit codes 0 succeeded · 1 failed · 2 protocolo · 3 blocked · 4 abandoned · 5 indeterminate · 124 deadline — y evidencia ausente o ambigua es indeterminate, nunca éxito.

06 · tu-flota

Cómo lo tienes cableado: agent-fleet-orchestrator

Regla del repo: frontier coordina, locales ejecutan en paralelo. Tu implementación sube un nivel sobre el cmux crudo: manifests con UUIDs, gates de fase, contratos de salida y presupuesto de recursos.

Ciclo de vida de un fleet

de cero a teardown
cmux ping && just status          # radar: ¿agentes ⚠️ esperándote desde ayer?
just fleet-preset audit audit       # bootea el roster canónico (o: just fleet <f> build=codex …)
just advance audit BUILD <gate-id>  # avanza de fase SOLO con evidencia
just send audit build "tarea acotada"
./scripts/fleet-dispatch.sh audit triage "clasifica esta evidencia…"   # worker local one-shot
./scripts/fleet-wait.sh audit build --run build=<run_id> --timeout 1800
just fleet-down audit               # teardown al mergear/abandonar — sin workspaces zombis
CONTROL→ RECON→ BUILD→ CHALLENGE→ VERIFY

Solo CONTROL y la fase activa reciben trabajo; avanzar congela las fases anteriores (BUILD no puede mutar un artefacto durante CHALLENGE/VERIFY), y salir de BUILD exige --approved-by <humano>. El manifest (orchestration/runs/fleet-<feature>.manifest) es la fuente de verdad rol → surface, y cada script compara sus UUIDs contra tree antes de cualquier efecto — una discrepancia falla cerrada.

El roster (router.yaml)

Presupuesto de memoria (M5, 16 GB): máximo un modelo local 7B+ en vuelo y tres workers locales concurrentes; nunca gemma4:26b, qwen3-coder:30b ni devstral:24b en local. Los workers locales no tienen filesystem ni shell: reciben un evidence pack acotado y responden por contrato — STATUS: DONE|BLOCKED|FAILED + SUMMARY / EVIDENCE / RISKS / NEXT_ACTION. Parsea STATUS antes de confiar en el resto.

Cuándo delegar (y cuándo no)

delega — fleet

“¿Qué se me escapa?”

Auditorías y reviews: siempre ≥2 workers con perspectivas distintas antes de tu veredicto. Cambios riesgosos por cerrar: una review frontier independiente obligatoria. ≥3 subtareas independientes: paraleliza. Búsqueda/clasificación a escala: fan-out a locales baratos.

hazlo tú — sin fleet

“Haz esto”

Tarea única secuencial, verificación pequeña contra código, cualquier cosa que un test responde barato, turnos conversacionales. Es el ~95% de los casos: la delegación es la excepción que paga, no el default.

07 · patrones

Patrones de orquestación probados

PatrónQué esCuándo
Three-tier Orquestador prompta a leads; leads promptan a workers. Panes ordenados por rango (CONTROL → … → VERIFY), síntesis siempre en el lead. Trabajo estructurado multi-fase; el patrón favorito de Dan.
Race just race <n> "<task>" — agentes heterogéneos compiten en la misma tarea; el primero en terminar es candidato, no verdad. --cancel-losers solo tras un gate de verificación. Hotfix / needle-in-a-haystack: “producción caída, respuesta YA”. El video lo demuestra con 8 agentes.
Broadcast fan-out La misma tarea (o particiones de ella) enviada a N panes a la vez; el orquestador cosecha y deduplica. Clasificación, búsqueda amplia, resúmenes a escala — workers locales gratis.
Doorbell / event loop Suscribirse a agent.hook + notification.created; dormir hasta el evento, leer una vez. Cualquier espera sobre >1 agente. Cero polling.
Boomerang El worker ejecuta y colapsa su contexto en un resumen breve para el orquestador (eficiencia de tokens). Cadenas largas donde el detalle intermedio ya no importa.
Supervisor loop Escalada temporal: nudge a los 3 min → restart a los 5 → abandonar tras 2 fallos. En tu repo: fleet-wait dispara ESCALATION por timeout y fleet-abandon libera leases. Flotas grandes donde algún worker siempre se atasca.
Pane analyzer Clasificar el estado de un pane con un LLM barato (20–360 tokens) + caché por hash de contenido. Dashboards de flota; detectar “needsInput” sin leer todo.

Los últimos tres vienen del ecosistema pi/cmux (spec de Joel Hooks, dmux, pi-coordination): vale la pena conocerlos aunque tu repo aún no los implemente — son la evolución natural del fleet-wait que ya tienes.

08 · practicas

Buenas prácticas — cada una con su cicatriz

Destiladas de tu propia adopción (2026-07): no son teoría, cada regla tiene un incidente detrás. Las diez que más pagan:

  • Problema primero, herramienta después. Adopta cmux cuando el arranque manual y la falta de acceso programático te duelan de verdad — no por hype.
  • Sube por la escalera. Manual → orquestador operando cmux → fleet con manifest → patrones (eventos, race). Cada nivel valida el anterior.
  • Verifica refs antes de actuar.un close-surface con ref obsoleta cerró el lead vivo; se restauró con claude --resume.
  • Contratos de salida + verificación frontier. Los modelos chicos marcan DONE con optimismo.gemma3 marcó DONE sin implementar nada — el lead parsea y verifica, no confía.
  • UUID antes de cada efecto. fleet-send/dispatch/wait/down comparan el UUID del manifest contra el tree actual; discrepancia = falla cerrada.
  • Higiene de secretos. Notificaciones al teléfono pasan por servidores de cmux (activa Hide content).un healthcheck de llaves dumpeó el environment al transcript; quedó silenciado.
  • Ganador ≠ correcto. La carrera da velocidad, no verdad: verifica la respuesta ganadora antes de actuar, especialmente en hotfixes.
  • Revisa tus colas de decisión.dos sesiones esperaron ~1h una elección humana sin que nadie lo notara — usa just status y cmux notify con "DECISION:".
  • Un workspace = una misión; teardown al cerrar. Workspaces zombis acumulan confusión y sesiones idle.
  • Codifica cada lección en la skill. .claude/skills/cmux/SKILL.md es memoria operativa: cada incidente se vuelve regla dura que el próximo orquestador hereda gratis.

Antipatrones

  • Token-maxing: 20 agentes en loop sin mirar qué hacen. Si no supervisas ni cosechas patrones, el fleet es teatro caro.
  • Scraping de pantallas como canal de datos entre agentes — las pantallas truncan; usa archivos.
  • Sleeps calibrados a mano en lugar de eventos.
  • Un workspace eterno con misiones mezcladas.
  • Merge/deploy confiado al fleet sin gate humano.
09 · vs-tmux-vs-warp

¿Tienes que usar cmux?

No. La ideología es lo transferible: acceso programático a los primitivos. La postura de Dan — y la de tus propios docs — es pragmática: tmux por estabilidad, cmux por construcción agéntica moderna, lado a lado.

cmuxtmuxWarp
Construido paraFlotas de agentes AI visibles y programablesMultiplexar terminales (1987→)Terminal con AI integrada para humanos
PlataformamacOS nativo (Swift + libghostty)Linux / macOS / BSD / casi todomacOS / Linux / Windows
Acceso programáticoCLI + socket: panes, teclas, pantalla, browser, eventos, notificacionesSí: send-keys, capture-pane, hooks — probado por décadasLimitado — orientado al humano en el teclado
Identidad visual de agentesSidebar, colores, badges, anillos de atención, agent panelStatus line configurable (a pulso)Bloques y temas, sin semántica de agente
Browser embebido scriptableSí (click, DOM, JS, sesiones importadas)NoNo
MadurezNuevo, se mueve rápidoRocaEstable, cerrado en lo agéntico
LicenciaGPL-3.0, open sourceISC, open sourcePropietaria
La regla de filtro de Dan para cualquier herramienta nueva: si no tiene acceso programático, la ignora por completo. “Es solo un terminal” también es la salvaguarda: cualquier agente CLI funciona, no hay lock-in, y tmux cubre lo mismo donde cmux no llega.
10 · escalera

La escalera de aprendizaje (31 prompts, 5 tiers)

El repo compañero del video valida cada capacidad con prompts en lenguaje natural ejecutados contra cmux vivo (v0.64.17), usando solo el loop de 4 verbos. Es el mapa para subir de nivel — y tu repo ya opera sólidamente en T3:

  1. Foundations (01–05)Crear workspaces, dividir panes en grillas, mapear la topología con tree.
  2. Driving one agent (06–10)Lanzar Claude Code / pi en un pane, inyectar credenciales vía .env, layouts declarativos (cmux.json).
  3. Fleet orchestration (11–16)Broadcast a 4 agentes a la vez, loops reactivos por eventos, poda por CPU. ← tu nivel actual, con gates y manifests propios.
  4. Browser integration (17–20)Surfaces de navegador que los agentes clickean, llenan y capturan; replay de sesiones para autenticación.
  5. Scale & resilience (21–25 + 26–31)Command centers multi-ventana, agentes remotos por SSH, recuperación de crashes, el capstone “Software Factory” (plan → fan-out → test → verify → teardown) y personalización total.

ritual diario
